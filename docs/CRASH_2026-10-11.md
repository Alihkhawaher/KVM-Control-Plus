# Out-of-memory crash: 2026-10-11

Two crashes, both fatal to the desktop, both caused by this app. This is what the
evidence says, what the code did, and what was changed. Every number here was read
out of Windows itself, not estimated.

## What happened

| time | process | committed memory | process ran for |
|---|---|---|---|
| 08:22:57 | `KVM-Control-Plus.exe` (pid 30168) | 485,745,373,184 B (452 GiB) | 10 h 30 m |
| 12:17:23 | `KVM-Control-Plus.exe` (pid 40428) | 478,142,341,120 B (445 GiB) | 5 h 55 m |

Source: `Microsoft-Windows-Resource-Exhaustion-Detector`, System log, event **2004** —
Windows' own diagnosis of a low virtual memory condition, naming the top consumers.
The crash-dump PE timestamp (`0x6acab314`) and SHA-256
(`58f42faf0e7795f30239f4af93cb532bff709e2d8271fb0d5c9939507afec42e`) match the
v0.1.2 release byte for byte, so the binary that died is the one that shipped.

This is not a "slow leak in a library" story: the process aborted because an
allocation failed, which Windows reports as **0xc0000409 with parameter 1 = 7**
(`FAST_FAIL_FATAL_APP_EXIT`) — that is Rust's allocator calling `process::abort()`
via `__fastfail`. The fault address is inside our own module, at RVA `0x36f201`.

Consuming the machine's whole commit charge broke everything else that needed to
allocate at that moment:

```
12:17:17  KVM-Control-Plus.exe   0xc0000409  (alloc failure)   <- this app
12:17:20  WhatsApp               0xc00000fd  (bad_module_info)
12:17:20  Everything service
12:17:25  dwm.exe                0xc00001ad  <- the desktop compositor
```

`dwm.exe` restarting is why the desktop reset, and why WebView2 apps left running
(WhatsApp) kept drawing into a window that no longer existed.

## The cause

Two facts, and a queue:

1. **Frames were handed to the UI through `std::sync::mpsc::channel()`**, which is
   **unbounded** — `send` never blocks and never fails while a receiver exists.
   Each frame is a decoded 1920×1080 RGB buffer: `1920 × 1080 × 3` = **6,220,800
   bytes**.
2. **The UI legitimately stops collecting.** A minimised or invisible window never
   receives `RedrawRequested` on Windows — eframe special-cases exactly this:

   ```rust
   /// Returns `true` if the window is invisible or minimized.
   /// These windows don't receive `RedrawRequested` events on Windows, ...
   pub fn is_invisible_or_minimized(window: &Window) -> bool
   ```

   So `update()` — and with it every drain of the queue — stops, while the capture
   thread keeps producing.

Together: every frame that arrives while the window is not being drawn is queued
and never freed, at the full frame rate, for as long as that lasts.

The memory is identifiable by arithmetic — both crashes are within 0.2% of a whole
number of frames:

```
478,142,341,120 / 6,220,800 = 76,861.9 frames
485,745,373,184 / 6,220,800 = 78,084.1 frames
```

Measured production rate on this machine (source asleep, so these are real decoded
frames of black): **~30 fps**, i.e. ~186 MB/s of growth, which reaches 478 GB in
**≈45 minutes** of a window that is not being drawn.

## Why it was not caught earlier

- The log ring buffer is bounded (4,000 lines, verified), the video texture is
  reused, and exactly one frame was retained by the UI: every *other* consumer of
  memory in the app was already bounded, which is why the queue went unexamined.
- The one line that would have named the failing allocation size — Rust prints
  `memory allocation of N bytes failed` to **stderr** — went to a console the GUI
  had deliberately given back to Windows. Nothing survived to read.
- v0.1.1 redrew continuously while capturing, which drained the queue aggressively;
  that masked the problem as long as the window was being drawn, but a repaint
  *request* cannot produce a paint on a minimised window, so the flaw was always
  there.

## The fix (v0.1.3)

Bounded by construction, and three separate defences:

| change | what it prevents |
|---|---|
| `video::mf::FrameSlot` — the newest frame replaces the waiting one, so the queue is **one frame long, always** | the unbounded growth itself |
| Producer backpressure — if nothing is collected for 2 s, the loop keeps reading samples but stops converting them | burning a core decoding frames nobody will see |
| `proc_mem` ceiling — committed memory checked once a second; past it, capture stops and says so (default 4 GiB, `KVM_MAX_COMMIT_MB` to override) | the next unknown cause from taking the desktop down |
| `%APPDATA%\KVM-Control Plus\last-run.log` — GUI runs write their log to a file, and stderr is aimed at it | the fatal message disappearing again |

The frame slot is also *more correct* than the queue was: live video wants the
newest frame, never a backlog, and a backlog is pure added latency.

## How to verify it

`--soak <seconds>` reproduces the exact fatal condition — a producer with **nobody
collecting** — and reports the process's committed memory while it happens:

```
$ KVM-Control-Plus.exe --soak 20
 t(s)   commit(MB)    produced   collected
    0          9.8          14           0
    1          9.9          31           0
    ...
   20          9.9          61           0

produced 61, collected 0, peak commit 18.8 MB, ceiling 4096 MB
PASS — 61 frames produced with nobody collecting, memory stayed flat
```

Note what happens between t=1s and the end: production stops. That is the
backpressure working — before, that column would have climbed forever, 6 MB at a
time.

The ceiling can be tested without putting the machine at risk:

```
$ KVM_MAX_COMMIT_MB=1 KVM-Control-Plus.exe -v --soak 8
[ERROR] committed 10 MB, past this app's 1 MB ceiling — capture stopped to protect the machine
```

Unit tests cover the same ground without hardware: the slot keeps exactly one frame
however many arrive uncollected, reports when nobody is collecting, and the ceiling
cannot be removed by a malformed override.
